一句话结论：当前烧录的 main.c 是一个 OLED 调试程序（死循环不返回），README 描述的 v0.6 业务闭环（采集→自适应阈值→决策→UDP 推送）当前根本没有运行；同时 MQ-2 火灾链路全程断开、TinyML 用缺传感器的数据训练、OLED 存在三套互相矛盾的引脚定义。建议先做 P0 恢复（约半天），再按 P1→P2 推进。

P0 · 阻断级问题（不修，产品功能不成立）

P0-1 main.c 是 OLED 测试死循环，业务代码全部不可达

User/main.c:163-212

OLED_DirectTest() 内部 while(1) 闪烁永不返回，其后的 SensorHub_Init / DecisionEngine_Init / AT_Init / AT_LearnBaseline 以及主循环全部是死代码。也就是说现在板子上电只会闪屏，不会采集、不会决策、不会联网告警。

修复：用备份里的业务骨架重写 main（v02.bak 也不是最新版，缺 AT 学习和键盘切模式），正确顺序应为：硬件初始化 → 可选外设（条件编译）→ SensorHub/Decision/AT 初始化 → 非阻塞式基线学习 → 主循环（键盘扫描/采集/AT_Update/决策/OLED 刷新/喂狗）。

P0-2 MQ-2 火灾检测链路全程断开，CheckFire 是死代码

sensor_hub.c:71 ｜ adc.c:126-131 ｜ decision_engine.c:167

采集被注释 // s_sensor_data.mq2_adc = ADC_ReadMQ2();，而 ADC_ReadMQ2() 本身直接 return 0，于是 mq2_adc 恒为 0；CheckFire 第一行 if (mq2_adc==0 …) return ALERT_NONE 永远提前返回，火灾永远不可能告警，AT 学到的烟雾基线也恒为 0。

// adc.c —— 硬件到位后：① GPIO 初始化 PA6 模拟输入 ② 打开下面这行
uint16_t ADC_ReadMQ2(void) {
    return ADC_ReadChannel(MQ2_ADC, MQ2_ADC_CHANNEL);   // PA6 / ADC1_IN6
}
// sensor_hub.c SensorHub_Update() 内：
    s_sensor_data.mq2_adc = ADC_ReadMQ2();

注意 MQ-2 半导体探头需要预热（数据手册通常建议数分钟），上电 20s 就学基线会把预热漂移学进去，基线学习应跳过或延后 MQ-2 通道。

main.c:42-45 ｜ oled.c:7-8,146 ｜ README ｜ oled_SPI_from_STM32F1.c

main.c 内联测试PB0PF11PB1PC13

同时 USE_OLED=1 但业务代码从未调用 OLED_Init() 和已经写好的 OLED_ShowHomeScreen()；目录里还残留 F1 移植文件 oled_SPI_from_STM32F1.c。必须按实际接线选定一套，删除 main.c 内联测试代码和 F1 残留，主循环统一调 oled.c 接口刷新。

P0-4 TinyML 模型在“缺 MQ-2”的数据集上训练，却默认启用

v1_train/training_report.txt ｜ scaler_params.h ｜ decision_engine.h:11

485 个样本中 mq2 / mq2_dev 两维恒为 0（mean=0，sklearn 把 0 方差替换成 std=1），模型从未见过烟雾特征；而 temp_dev 的 std=0.0957、humi 相关维度方差极小，实测温湿度稍偏，标准化后被放大几十倍，边界地带 40–80cm 的入侵判断极易误报。报告指标 Recall=1.0 也说明模型偏向“一律报异常”。

修复：MQ-2 接通后重新采数、重训并重新导出两个 .h；在此之前把 USE_ML 置 0，纯规则运行，避免残模型参与决策。另外推理头文件在 Hardware/ML 与 v1_train 各存一份，必须只保留一份，防止改漏。

P0-5 光敏“数值越大越亮/越暗”三处注释互相矛盾，自动照明方向存疑

README 硬件表 ｜ adc.c:114 ｜ sensor_hub.h:7 ｜ decision_engine.c:188-192

README 写“光照越强值越大”，adc.c 与 sensor_hub.h 写“光照越强值越小”。而 AutoLighting 直接用 light_adc × PERIOD/4095 当占空比（PWM 还是低电平点亮、极性 Low）：方向一旦搞反就是“白天灯最亮、夜里熄灭”。需用万用表/串口实测一组明/暗 ADC 值确定方向，再决定是否取反（4095-light_adc），并统一三处注释。

P1 · 可靠性与正确性问题

P1-1 全阻塞超级循环，任一慢操作卡死全系统

adaptive_threshold.c:91 ｜ hcsr04.c:75-97 ｜ dht11.c:64 ｜ esp8266.c:86 ｜ matrix_key.c:129

阻塞点清单：基线学习 delay 20s；HC-SR04 忙等最长 60ms；DHT11 起始信号 20ms；ESP8266 连 WiFi 单次等待 15s；Key_Scan 松手等待 while(…); 无超时，按住键或行列短路时整机死锁；ADC 等 EOC（adc.c:97）、USART 等 TXE 也都是无超时 while。

短期：所有 while 加超时计数并返回错误码；Key_Scan 改“按下沿触发 + 状态机消抖”，删掉松手死等和硬编码 16800 空循环延时（用 g_tick/delay 模块）。中期：上 FreeRTOS 或时间片调度（见 P2）。

P1-2 没有看门狗，Fault 处理是空死循环

stm32f4xx_it.c:67-112 ｜ 全工程无 IWDG

安防设备死在任何阻塞 while 或跑飞进 HardFault 后永久失效，且没有任何现场信息。建议：① 启用 IWDG（如 1s），主循环喂狗，阻塞操作分段喂狗；② HardFault_Handler 里读取堆叠的 PC/LR/CFSR 通过 USART1 打印后再复位（NVIC_SystemReset），便于定位。

P1-3 ESP8266 下行解析状态机遇逗号即归零，远程控制永远收不到

esp8266.c:235-249

固件实际下发的是 +IPD,<len>:<data>（多连接时为 +IPD,0,<len>:）。状态 4 只接受数字和冒号，遇到逗号立刻 state=0，因此一帧都解析不出来。需要兼容“逗号 + 可选连接号 + 逗号”的语法，再解析长度与冒号。

P1-4 DHT11 失败恢复逻辑会误覆盖真实 0 值，且依赖浮点相等比较

sensor_hub.c:57-66 ｜ dht11.c:163-167

DHT11_Read_Data 失败时先把输出写成 0.0，上层再用 == 0.0f 判断并恢复默认值——真实 0°C/0%RH 会被误改，且“靠输出值反推失败”本身不可靠。正确做法：失败时函数不要触碰输出参数，上层保留上一次有效值即可。

// dht11.c：失败直接 return，不写 *temperature / *humidity
if (ret != 0) return 1;
*humidity = (float)data[0];
*temperature = (float)data[2];

P1-5 HC-SR04 整数除法丢精度，且实现与 README 描述不符

hcsr04.c:111 ｜ README“PC6 中断测 Echo”

(float)(time_us / 58) 先做 uint32 整除再转浮点，距离分辨率只有 1cm；应为 time_us / 58.0f（精确系数 58.02）。另外 README 声称 Echo 用定时器输入捕获/中断测量，实际是 delay_us 忙等轮询，文档需与实现统一（建议改 TIM 输入捕获，彻底不阻塞 CPU）。

P1-6 告警“一次命中即触发”，缺少连续确认，超声波尖峰会误报

decision_engine.c CheckIntrusion

建议加滑动确认窗：连续 3 次采样（1.5s）中 ≥2 次命中才置告警，恢复也要求连续 N 次正常，可显著抑制瞬时噪声并避免蜂鸣器/网络抖动。

P1-7 阈值参数三处不一致，硬编码散落

adaptive_threshold.h:29-31 ｜ decision_engine.c:40-42,154 ｜ README
参数头文件decision_engineREADME
EWMA α0.01—0.1
距离突变30cm20cm（另硬编码 80/30）15cm
σ 系数 Kint 3—3.0f

所有阈值集中到 adaptive_threshold.h，用 3.0f 浮点字面量；decision_engine 不再自定义第二套 40/80/20，避免两条入侵规则边界重叠、绕来绕去。

P1-8 mq2_sigma=0 时 EWMA 永久冻结

adaptive_threshold.c:149-152

条件 fabsf(diff) < 2.0f*sigma，当 sigma=0（当前必然，因为 MQ-2 恒 0）时恒为假，EWMA 与阈值永不更新。需要对 sigma 设下限（如 max(sigma, 1.0f)），并在 MQ-2 未接入时直接跳过该通道更新。

P1-9 编译警告未清零，且有乱码字节进了源码

build_log.txt ｜ decision_engine.c:124（#870-D 非法多字节序列）

当前 0 Error 但 2 Warning：未使用变量 buf[32]；“入侵告警！距离”处有损坏字节。按项目约定全部源码统一 UTF-8 with BOM，删未用变量，做到 0 Warning——警告是面试时被翻代码的第一扣分项。

P1-10 WiFi 凭据明文硬编码进固件

esp8266.h:24-25

SSID/密码随源码分发即泄露。抽到独立 wifi_config.h.example（真实文件不入库），或后续用矩阵键盘 + Flash 实现首次配网；同时建议工程根目录补 .gitignore（Object/、*.bak、JLinkLog.txt、__pycache__/）。

P1-11 UDP 告警“发了就算成功”，可能静默丢失

esp8266.c:170-171,179-196

CIPSTART 失败被硬编码 return 1；CIPSEND 发完数据不等 SEND OK；告警帧没有序号、时间戳、设备 ID，丢包后上位机无感知。建议：等待发送结果应答、JSON 加 seq/ts/device、关键告警应用层重发 2–3 次（间隔由现有冷却机制控制）。

P1-12 三个串口的 Printf 共用同一个 static 缓冲区，不可重入

usart.c:33

USART1/USART2_Printf 共用 printf_buf[128]，一旦在中断或嵌套场景调用会互相踩内存。改为每个串口独立缓冲，或统一一个带互斥保护的格式化函数；长中文日志注意 128 字节截断。

P2 · 架构升级与产品化

#方向具体做法与价值
P2-1FreeRTOS 多任务采样任务（500ms）、决策任务、通信任务、UI 任务分离，队列传递 Sensor_Data_t；ESP 连网/AT 阻塞不再卡采集与按键。README 路线图已规划，这是面试最大的架构加分项。
P2-2掉电存储当前模式/基线/阈值重启全丢、每次上电学 20s。不必等 W25Q128，先用 STM32F407 内部 Flash 最后一页存结构体（CRC 校验），上电直接恢复。
P2-3传感器自检HC-SR04 连续 N 次 err 应上报告警“传感器离线”而不是静默；DHT11 连续失败计数；MQ-2 预热状态机。安防产品“故障安全 fail-safe”是必答题。
P2-4模式语义补全SLEEP 当前与 AWAY 完全相同：应关自动照明/降亮度；利用现成 4×4 键盘做“撤防密码”，输错触发告警。
P2-5告警分级声响Beep_PlayNote/SetFreq 已实现却没用：入侵急促间歇、火灾连续双音，OLED 同步显示（OLED_ShowHomeScreen 已写好，主循环没接）。
P2-6实时数据上屏ESP8266_SendData 已写但主循环没调用；Dashboard 目前只有告警，增加 2s 一次的传感器数据流，形成“实时监控 + 告警”双面板。
P2-7分层解耦sensor_hub.c（下层）#include 了 decision_engine.h（上层），反向依赖应删除；SERVO 空实现、RTC（#if 0，Wakeup bug）决定补全或移除。
